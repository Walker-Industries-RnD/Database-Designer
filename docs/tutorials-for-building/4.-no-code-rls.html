4. No Code RLS

Row Level Security (RLS)

RLS lets the database itself decide which rows each user can see and change, so a bug in your API can't leak someone else's data. For a walkthrough of the editor, see 11. Securing Your Data With The RLS Editor. This page covers what gets generated and how to use it.

What a policy is made of

Each policy in the RLS Editor has:

Setting Options
Command ALL, SELECT, INSERT, UPDATE or DELETE
Access Own rows; Public read, own writes; Everyone; Nobody; Custom SQL
Owner column The column that says who a row belongs to, such as user_id. Leave it empty and it's guessed

When the owner column is empty, the first of these that exists on the table is used: user_id, owner_id, created_by, author_id, seller_id, account_id, profile_id, member_id, sender_id, buyer_id, customer_id. On a table whose name contains "user", "account" or "profile", the primary key is used. If nothing fits, the editor warns you, because then only admins would see the rows.

Under each policy is a line that says in plain words what it allows, for example "standard_users may SELECT only rows where user_id = the current user (admins/moderators bypass)".

What RLS.sql contains

  • A database role for each role in the editor. Standard Users becomes standard_users.
  • Helper functions: current_user_id(), is_admin() and is_moderator().
  • ENABLE ROW LEVEL SECURITY on every table that has policies.
  • The policies themselves, plus the GRANTs each role needs.

Admins can read and write every row. Moderators can read every row but only write their own. Everyone else gets what their policies allow.

RLS.sql drops and recreates its policies, so it's safe to run again after every build. Run it after SQL.sql.

Telling the database who's asking

The policies read two settings: the current user's id and their role. Set both at the start of every request, on the same connection:

SELECT set_config('app.current_user_id', '42', false);
SELECT set_config('role', 'standard_users', false);

In NodeWalker, the DB: RLS Set User and DB: RLS Set Role blocks do exactly this. DB: RLS Reset User clears them again.

Connect as an ordinary role

Superusers, and roles with BYPASSRLS, ignore every policy. If you connect your API as postgres, RLS does nothing. Make a normal login role that is a member of the generated roles and connect with that.

Custom SQL

Pick Custom SQL when the other options don't fit. You write the USING part (which rows can be seen or changed) and optionally the WITH CHECK part (which rows can be written). For example:

user_id = current_user_id() OR is_public

Policy graphs

Every policy also has an Open in NodeWalker button. RLS.sql is built from the settings above, not from the graph, so use the graph for extra logic you want to keep next to the policy.
