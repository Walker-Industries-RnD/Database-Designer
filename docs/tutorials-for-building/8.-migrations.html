8. Migrations

Once your database has real data in it, you can't just drop it and run SQL.sql again. Migration.sql upgrades the database you already have to match your latest design.

How it works

Every build saves a schema.snapshot.json next to its SQL. The next build compares your project with that snapshot and writes Migration.sql: the statements that turn a database built from the previous build into one that matches this build.

So GeneratedDB\v5\Migration.sql upgrades a database built from v4.

What it handles

  • new tables and new columns
  • changed types, defaults, Not Null, Unique and Check constraints
  • new and removed foreign keys
  • new and removed indexes

Everything runs in one transaction. If any statement fails, nothing is changed.

What it won't do on its own

Dropping a table or a column deletes data, and a rename looks exactly like a drop plus an add. So those statements are written but commented out. Read them, uncomment the ones you really mean, and for a rename, replace the drop and add with:

ALTER TABLE store.products RENAME COLUMN title TO name;

Changing which column is the primary key is also left to you. The migration lists it at the top with the statements you'll need.

Running it

  • In Database Designer: Local Database > Apply Migration.sql.
  • By hand: psql -d yourdatabase -f Migration.sql.

Run RLS.sql again afterwards if you changed any policies. It's safe to run more than once.

Tips

  • Build after each set of changes, so each migration stays small and easy to read.
  • Skipped a version? Run each migration in order (v4, then v5, then v6).
  • Adding a Not Null column to a table that already has rows needs a default, or the migration will fail on the existing rows.
  • Always try a migration on Local Database before running it on a live database.
