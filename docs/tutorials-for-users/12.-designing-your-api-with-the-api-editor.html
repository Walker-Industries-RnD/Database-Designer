12. Designing Your API With The API Editor

Your database holds the data, and your API is how apps and websites talk to it. The API Editor lets you plan that API: group related routes into modules, give each module its endpoints, and give each endpoint the functions (the actual GET, POST and so on) that do the work. When you build your project, this becomes a real ASP.NET Core API with Swagger.

Opening the API Editor

From the main desktop, open the API Editor app.

Like the RLS Editor, it works in three steps: Modules, then Endpoints, then Functions.

💜 Modules are just folders for your routes.

A module is nothing scary. It's a bucket of related endpoints. Everything about signing in goes in Auth, everything about accounts goes in Users, and so on. Organize now, thank yourself later.


Step 1: Modules

The editor starts with four modules:

  • Auth
  • Users
  • Data
  • Admin

You can rename them, give them a description and an icon, and add or remove modules as you need. Pick a module and move on to its Endpoints.

Step 2: Endpoints

An endpoint is one area inside the module, like Login, Profile or Orders. Give each one a description, then move on to its Functions.

Step 3: Functions

A function is one thing the endpoint can do. Each function has:

Field What it's for
Name A short label, like Sign In or List Orders
Verb GET, POST, PUT, DELETE or PATCH. Each has its own color
Description What the function does. It shows up in Swagger
Tag Optional, for your own grouping

💜 Pick the right verb.

Quick rule of thumb: GET reads, POST creates, PUT/PATCH updates, DELETE removes. Get these right and your API is easy to guess. The colors in the editor make a wrong verb jump right out.


Building the logic (NodeWalker)

Each function's logic is built in NodeWalker. Press Open in NodeWalker on a function, and wire up what it does: read from a table, check the input, save something, return a result. See 2. NODEWLKR for how.

You can test a function straight away with ▶ Run in NodeWalker, once you've set up 7. Testing With Local Database.

From design to a running API

When you build the project, each function becomes a route:

POST  api/<module>/<endpoint>/<function>

Names are lower-cased and spaces become dashes, so the Cancel function under Orders in the Store module is POST api/store/orders/cancel. The inputs of its NodeWalker graph become the route's parameters.

Functions without a graph still get a route. It answers "Not implemented yet" until you build the logic.

To run the API, press Start API in Local Database, or see 3. No Code API for running it yourself.

Saving

Press Save to store your API design. It's kept with your project, so it's included when you export or make a template (together with the NodeWalker graphs), and it loads again the next time you open the API Editor.

Tips

  • Group by feature, not by table. An Auth module can touch several tables, and that's fine.
  • One function, one job. Small functions are easier to build and to test.
  • Match verbs to what the function does, so the API and Swagger stay predictable.
  • Keep names short and clear. They become your route names.
