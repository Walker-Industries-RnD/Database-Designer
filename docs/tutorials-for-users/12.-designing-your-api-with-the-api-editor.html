12. Designing Your API With The API Editor

Your database holds the data — your API is how the outside world talks to it. The API Editor lets you map out that API visually: group related routes into modules, give each module its endpoints, and give each endpoint the functions (the actual GET/POST/… operations) that do the work. When you build your project, this design feeds straight into a real ASP.NET Core API with Swagger docs.

Opening the API Editor

From the main desktop, open the API Editor app.

Like the RLS Editor, it's a resizable window with a three-step flow: Modules → Endpoints → Functions.

💜 Modules are just folders for your routes.

A module is nothing scary — it's a bucket of related endpoints. Everything about signing in goes in Auth, everything about accounts goes in Users, and so on. Organize now, thank yourself later.


Step 1 — Modules

The editor opens on Modules, pre-seeded with four to start from:

  • Auth
  • Users
  • Data
  • Admin

For each module you can rename it, give it a description, add an icon, and add or remove modules as needed. Pick a module and continue to its Endpoints.

Step 2 — Endpoints

An endpoint is a named area of the module — think of it as a resource or a route group (e.g. "Login", "Profile", "Orders"). Give each one a description, then drill into its Functions.

Step 3 — Functions

A function is a single operation on that endpoint. Each function has:

Field What it's for
Name A short label, e.g. "Sign In" or "List Orders"
Verb The HTTP method — GET, POST, PUT, DELETE, or PATCH. Each verb is colour-coded so the list reads at a glance
Description What the function does
Tag Optional marker for your own grouping

Add one function per thing the endpoint can do.

💜 Pick the right verb.

Quick rule of thumb: GET reads, POST creates, PUT/PATCH updates, DELETE removes. Getting these right makes your API predictable — and the colours in the editor make a mismatched verb jump right out.


Building the actual logic (NodeWalker)

Just like RLS policies, each function's logic is built visually. Every function has an Open in NodeWalker button.

  1. Click Open in NodeWalker on a function.
  2. The node-graph editor opens, tagged with that function's name.
  3. Wire up what the function does — read from a table, validate input, return a result, and so on.

From design to a running API

When you go to the Build page and build your project, the API design isn't just documentation — it's used to generate a real ASP.NET Core project, complete with Swagger / OpenAPI so every module, endpoint and function shows up as browsable, testable routes.

Saving

Use Save in the editor to store your API design. It's kept with your project (in the project's session), so it exports and templates alongside everything else — including the node graphs — and reloads automatically next time you open the API Editor.

Tips & Best Practices

  • Group by feature, not by table. An "Auth" module can touch several tables; that's fine.
  • One function = one job. Small, single-purpose functions are easier to wire up and reason about.
  • Match verbs to intent so the generated API and Swagger docs stay clean and conventional.
  • Keep names human — they become your route names and show up in the generated Swagger UI.
