11. Securing Your Data With The RLS Editor

Row-Level Security (RLS) decides who is allowed to see or change which rows in your tables. Instead of every user being able to read everything, you write rules like "a user can only read their own profile" or "only admins can delete posts". The RLS Editor lets you lay all of that out visually, per role and per table, and then build the actual rule logic in the node graph.

Opening the RLS Editor

From the main desktop, open the RLS Editor app.

It opens as a resizable window with a simple three-step flow: Roles → Tables → Policies.

💜 Think in roles first!

RLS is easiest when you start from who's asking. A "Standard User" and an "Admin" should almost never have the same permissions. Get your roles right and the policies mostly write themselves.


Step 1 — Roles

The editor opens on the Roles page, pre-seeded with four common roles to get you moving:

  • Standard Users
  • Admin Users
  • Moderator Users
  • Bot Users

For each role you can:

  • Rename it and give it a description.
  • Add a small icon so it's easy to spot.
  • Add or remove roles to match your app.

Pick a role, then continue to its Tables.

Step 2 — Tables

Here you choose which tables this role has policies on. Each table gets its own description so you remember what the rules are protecting.

Select a table to drill into its Policies.

Step 3 — Policies

A policy is a single named rule for this role on this table. Each policy has:

Field What it's for
Name A short label, e.g. "Read own profile"
Category Groups the policy — Base Server, Profiles, Communication, or Economy. Each category is colour-coded so the list is easy to scan
Description Plain-English explanation of what the rule allows
Tag Optional marker for your own organization

Add as many policies as the role needs on that table.

Building the actual rule (NodeWalker)

A policy's name describes the rule — the logic is built visually. Every policy has an Open in NodeWalker button.

  1. Click Open in NodeWalker on a policy.
  2. The node-graph editor opens, tagged with that policy's name.
  3. Wire up the condition that decides when the policy passes — for example, "the row's user_id equals the current user".

NodeWalker turns your graph into a real predicate (the "does this row pass?" check) behind the scenes, so you never have to hand-write SQL policy expressions.

💜 One policy, one graph.

Keep each policy focused on a single idea. "Read own rows" and "Admins read all rows" are two policies, not one giant tangled graph. Small rules are easier to read, test, and fix later.


Saving

Use Save in the editor to store your RLS design. It's kept with your project (in the project's session), so it travels with the project when you export or template it — and it's reloaded automatically the next time you open the RLS Editor.

Tips & Best Practices

  • Deny by default. Only add policies for what a role should be able to do; anything you don't grant stays locked.
  • Name policies for the intent, not the mechanism — "Edit own comments" beats "policy_3".
  • Reuse categories consistently (Profiles, Economy, …) so large designs stay scannable.
  • Revisit RLS after you add new tables — a new table with no policies for a role means that role gets nothing on it.
