11. Securing Your Data With The RLS Editor

Row Level Security (RLS) decides who can see or change which rows in your tables. Instead of every user being able to read everything, you set rules like "a user can only read their own profile" or "only admins can delete posts". The RLS Editor lets you lay that out per role and per table, and the build turns it into real Postgres policies.

Opening the RLS Editor

From the main desktop, open the RLS Editor app.

It works in three steps: Roles, then Tables, then Policies. Use the Next and Back buttons at the bottom to move between them.

💜 Think in roles first!

RLS is easiest when you start from who's asking. A "Standard User" and an "Admin" should almost never have the same permissions. Get your roles right and the policies mostly write themselves.


Step 1: Roles

The editor starts with four common roles:

  • Standard Users
  • Admin Users
  • Moderator Users
  • Bot Users

You can rename them, give them a description and an icon, and add or remove roles to match your app. Pick a role, then press Next: Tables.

Admins and moderators are special: admins can read and write every row, and moderators can read every row. You don't need to write policies for that.

Step 2: Tables

Choose which tables this role has policies on, and give each one a description so you remember what it's protecting. Pick a table and press Next: Policies.

Step 3: Policies

A policy is one rule for this role on this table. Type a name and press Add Policy, then set:

Setting What it's for
Command What the rule covers: ALL, SELECT (read), INSERT (add), UPDATE (change) or DELETE
Access Who gets which rows (see below)
Owner column The column that says who a row belongs to, like user_id. Leave it empty and Database Designer guesses
Category Base Server, Profiles, Communication or Economy. Each has its own color so a long list is easy to scan

The Access options:

Access Means
Own rows Users only see and change rows they own
Public read, own writes Everyone can read, but users only change their own rows
Everyone No limit for this role
Nobody This role gets nothing
Custom SQL You write the rule yourself

Under each policy is a line that says in plain words what it allows, for example "standard_users may SELECT only rows where user_id = the current user". If it warns that there's no owner column, set one, or only admins will see those rows.

💜 One policy, one idea.

Keep each policy focused. "Read own orders" and "Everyone can read products" are two policies, not one giant tangled one. Small rules are easier to read, test and fix later.


Saving and building

Press Save to store your RLS design. It's kept with your project, so it's included when you export or make a template, and it loads again the next time you open the RLS Editor.

When you build the project, everything here becomes RLS.sql. How that file works, and how your API tells the database who's asking, is in 4. No Code RLS.

Tips

  • Deny by default. Only add policies for what a role should be able to do; anything you don't allow stays locked.
  • Name policies for what they allow. "Edit own comments" beats "policy_3".
  • Use the same categories across tables so big projects stay easy to scan.
  • Check again after adding tables. A new table with no policies for a role means that role gets nothing from it.
  • Run Build Check. It warns about policies for tables that don't exist and tables with no owner column.
